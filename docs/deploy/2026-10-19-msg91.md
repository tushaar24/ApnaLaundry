# Login OTP: Firebase → MSG91 (2026-10-19)

The owner wants login OTPs sent by **MSG91** instead of Firebase phone auth.

**Can it be done from the backend alone?** Only partly:
- **Changed by the backend alone:** the website and pre-Firebase app builds (before 11 Oct). They send every OTP through the backend's `request-otp` / `verify-otp`.
- **Needs app 1.0.14:** builds from 11 Oct to 1.0.13. They send real numbers' OTPs through Firebase on the phone and never ask the backend.
  - **App 1.0.14** asks the backend first, so from 1.0.14 the choice is a server switch.

## Backend: LIVE 2026-10-19 10:31 IST (server commit b5c7229)

- Patch: `2026-10-19-backend-msg91-otp.patch`. Deploy: `2026-10-19-msg91-deploy.sh`.
- Backup: `~/backend-filebak/20261019-050133-msg91`. The `.env` backup from before the creds were added: `~/backend-filebak/20261019-045949-msg91-env`.
- `laundry-auth.js` is patched but **not committed** on the server, because it carries older uncommitted live edits. Only `services/laundry-otp.js` and `config/env.js` are in b5c7229.

What the patch adds:
- An `msg91` OTP provider (`services/laundry-otp.js`), using MSG91 OTP v5:
  - `POST /api/v5/otp` sends a 6-digit code that expires in 5 minutes, using the DLT template.
  - `GET /api/v5/otp/verify` checks the code.
  - The auth key goes in the `authkey` header.
- `request-otp {phone, firebaseOk: true}` (sent by app 1.0.14+) returns one of:
  - `{method: "firebase"}`, with nothing sent, while `LAUNDRY_OTP_APP_METHOD` is unset;
  - `{method: "sms", challengeId, …}`, after the backend sends the SMS itself, when `LAUNDRY_OTP_APP_METHOD=sms`.
  - Review numbers `10000000xx` keep the deterministic OTP. Older clients never send `firebaseOk` and see no change.
- Test routes `POST /api/laundry/auth/test-msg91/send {phone}` and `/test-msg91/verify {phone, otp}`:
  - They need the `X-Test-Secret` header (`LAUNDRY_2FACTOR_TEST_SECRET`); without it they return 404 or 401.
  - They always use MSG91, never log anyone in, and return MSG91's raw reply.

`backend/.env` (set over ssh stdin, **never in git**):
- `LAUNDRY_MSG91_AUTH_KEY`, `LAUNDRY_MSG91_TEMPLATE_ID`, `LAUNDRY_MSG91_SENDER_ID`.
- The sender id (DALYAP) is set on the MSG91 template itself; the backend doesn't send it.
- **Rotate the auth key in the MSG91 panel** (it was pasted in chat), then update `.env` and recreate the backend.

The deploy was inert: `LAUNDRY_OTP_PROVIDER=minimoth` and `LAUNDRY_OTP_APP_METHOD` unset, so every login works as before.

## Switch-over (owner)

1. **Test on a real phone** first (from the server; the secret is never printed):
   ```sh
   docker exec shweta-makeup-monorepo-backend-1 sh -c 'wget -qO- --header "content-type: application/json" --header "x-test-secret: $LAUNDRY_2FACTOR_TEST_SECRET" --post-data "{\"phone\":\"98XXXXXXXX\"}" http://localhost:5001/api/laundry/auth/test-msg91/send'
   # then /test-msg91/verify with {"phone":"98XXXXXXXX","otp":"123456"}
   ```
2. **Website + old apps → MSG91:** in `backend/.env`, set `LAUNDRY_OTP_PROVIDER=msg91`, then run `docker compose -f docker-compose.prod.yml up -d --force-recreate backend`.
   - The website on the server has no Firebase code, so its login moves to MSG91 here.
   - OTPs already sent through minimoth in the last 5 minutes stop verifying; those users just tap Resend.
3. **App 1.0.14+ → MSG91:** add `LAUNDRY_OTP_APP_METHOD=sms` to `.env` and recreate the backend. Remove the line to go back to Firebase.
   - The app falls back to Firebase if the backend is unreachable or MSG91 fails (`OTP_UNAVAILABLE`).
   - The backend's limits still apply: a 30 s resend cooldown and 10 OTPs a day per phone.

Builds 1.0.11 to 1.0.13 keep using Firebase until those owners update.

## App 1.0.14 (prod)

- `AuthRepository.requestOtp` asks `request-otp {firebaseOk: true}` first for real numbers. Depending on the reply it builds a backend challenge (`Challenge.Backend(sms = true)`), returns the server's limit message, or falls back to Firebase.
- **Autofill uses the SMS User Consent API** (`SmsOtpConsent` in `LoginAutofill.kt`). It needs no app hash in the DLT template: Android shows "Allow MyLaundry to read this message?" and one tap fills in the code and logs in.
- New CleverTap event `OTP Sent {method: firebase | sms | review}`.

## Switched 2026-10-27 11:09 IST: website + old apps → MSG91

- **Test first:** `test-msg91/send` to 9971631166 (owner's choice) returned MSG91 `type: success` (request 366a416b68356335437a544a).
- **Change:** `LAUNDRY_OTP_PROVIDER=msg91` in `backend/.env` (backup `backend/.env.bak-otp-msg91-20261027-053918`), then `up -d --force-recreate backend`.
- **Checked after:** healthy; real numbers → msg91, review numbers → review. `LAUNDRY_OTP_APP_METHOD` is still unset, so app 1.0.14+ keeps Firebase.
